# IMEI による端末・登録者管理

## 識別と公開入口

端末は IMEI 全桁（15桁の文字列）を主キーとする。鍵・計測ログ・状態・証明書・登録者の期間は IMEI へひも付ける。端末の UUID は使わない。複数 IMEI を持つ端末は `device_imei_aliases` で同じ主 IMEI に解決し、別端末として重複登録しない。

`GET /certificates/{imei}` はその端末の現在の登録者に属する最新の有効な証明書を JSON で返す。副 IMEI でも同じ証明書を取得できる。Web の公開ページと QR は `/certificates/{imei}` を入口にする。Web のページ・QR 描画はこのバックエンドでは生成しない。

持ち主が替わると、新しい登録期間の証明書が発行されるまで公開入口は404になる。旧登録者の証明書を新登録者の現在の証明書として返さない。旧証明書は削除せず、`/api/certificates/{証明書UUID}` または従来の短い番号で参照できる。証明書 UUID は発行履歴の識別子で、端末の管理には使わない。

## API

利用者のアカウントやログインは作らない。最初にチャレンジを取得し、`POST /api/auth/devices` へ IMEI と Android の公開鍵・attestation・所有確認用署名を送り、アプリ用の認証情報を取得する。鍵の登録・検索・失効は端末用アクセストークンを持つアプリだけが使う。登録者はサーバーが管理するアプリ登録から決まり、JSON や任意の所有者ヘッダーからは受け取らない。

```http
POST /api/devices
Authorization: Bearer <access token>
Content-Type: application/json

{"imeis":["490154203237518"],"public_key":"-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n","proof":{"challenge_id":"<チャレンジID>","certificate_chain":["<DERをBase64>","<中間証明書・ルート>"],"signature_der":"<署名DERをBase64>"}}
```

- IMEI は1〜4個。15桁の数字とチェックディジットを検査し、重複を除去する。認証情報を発行した IMEI を主 IMEI とし、既存の主 IMEI を維持する。
- 既に別々の端末へ登録された IMEI の組み合わせは409で拒否し、自動で統合しない。
- 鍵は P-256 の公開鍵（PEM SubjectPublicKeyInfo）、署名方式は ES256。形式を検査して保存する。Google の信頼ルート、失効状態、ハードウェア鍵、起動状態、アプリ情報、チャレンジと所有確認用署名を検証する。計測ログ署名検証は #3 で実装する。IMEI 自体の検証範囲は通常の key attestation と区別する。
- 同じ登録者が同じ鍵で再送した場合は同じ登録期間と鍵を返す。同じ登録者の鍵交換では旧鍵を失効して履歴を保持する。
- 応答は `imei`、`imeis`、`ownership_id`、`registered_at`、`last_verified_log_at`、`reclaimable_at`、`key_id`。所有者の認証情報は返さない。

```http
POST /api/devices/lookup
Authorization: Bearer <access token>
Content-Type: application/json

{"imei":"490154203237518"}
```

現在そのアプリに登録され、公開鍵の登録が完了した端末だけを返す。他人の端末と不存在はともに404。公開証明書を見る場合は `/certificates/{imei}` を使う。

## 別の登録者への切り替え

前の登録者の最後の**検証済み計測ログのサーバー受信から15日（15×24時間）以上**経過したら再登録できる。ちょうど15日経過した時点から許可する。ログ未受信の場合は登録時刻を基準にする。

検索、認証情報の更新、同じ登録者の鍵の再登録・鍵交換、未検証ログでは活動時刻を更新しない。クライアントの取得日時は待機期間の判定に使わない。

切り替えでは旧登録期間・認証情報・旧鍵・有効な証明書の失効と、新登録期間・認証情報の発行を1トランザクションで行う。新しい公開鍵も初回登録時に同時に保存する。過去のログ・証明書・鍵は残す。IMEI のロックと端末行のロックで同時登録を直列化し、同時に2人へ切り替わらないようにする。ログの受信も同じ端末行をロックし、切り替え後の旧登録者のログを拒否する。

15日経過だけでは自動失効しない。別の登録者が再登録した時点で切り替え、旧登録期間の有効な証明書も `revoked` にする。

`signature_verified_at` は今後のログ取り込み処理が署名検証に成功した場合だけ設定する。DB が受信時刻を設定し、`last_verified_log_at` を更新する。現状はログ受信・署名検証 API が未実装なので、新規登録の待機期間は登録時刻から進む。

## 現在の登録者による手動失効

売却や譲渡の際は、現在の登録者が次の API を呼ぶと15日待たずに登録を終了できる。

```http
POST /api/devices/490154203237518/revoke
Authorization: Bearer <access token>
```

成功は204（本文なし）。主 IMEI・副 IMEI のどちらでも同じ端末の登録を終了する。認証済みの現在の登録者だけが操作でき、別端末の有効なトークンでの操作や不存在は404、不正な IMEI は400、不正・失効済み・旧登録者のトークンは401となる。

登録期間の終了、利用中の鍵の失効、その登録期間の有効な証明書を `revoked` にする処理を1トランザクションで行う。公開入口は404になり、次の利用者は 新しいチャレンジ・鍵・検証証跡を用意し、`/api/auth/devices` ですぐ再登録できる。旧鍵によるログは受け付けない。旧登録者が再送しても、新登録者の登録は失効しない。

過去のログ・ハッシュ・署名・証明書スナップショットは削除しない。証明書 UUID / 番号による過去参照では `status: "revoked"` を返す。認証情報だけの失効は `/api/auth/revoke`、証明書1件だけの失効は `/api/certificates/{number}/revoke` で行う。

## 認証との接続

ログインなしの発行・更新・失効、Android の呼び出し順と、書き込み時の権限確認は [authentication.md](authentication.md) を参照。外部 JWT の検証設定は使わない。再登録の15日ルールは `/api/auth/devices` で判定し、鍵登録 API ではその認証情報の対象端末だけを操作できる。

## 既存データの移行

`000002_imei_device_management` で既存の UUID 外部キーを IMEI へ移す。初期マイグレーションは変更しない。payload・署名・ハッシュ・証明書のスナップショットは変更しない。

既知の Pixel 8 デモだけは架空の IMEI `000000000094821` に対応付ける。デモ以外の既存端末がある場合は、マイグレーション前に `db/prepare-imei-migration.sql` を実行し、旧 UUID と確認済みの IMEI 全桁を `device_imei_migration_map` に登録する。末尾4桁や UUID から全桁を推測しない。CLI は対応不足を適用前にエラーとし、DB を dirty に進めない。

旧ログの受信時刻だけでは署名検証済みか分からないため、移行時に検証済みへ昇格させない。旧データの登録者は `legacy-import` / `unclaimed` とし、実在の利用者に推測で帰属させない。旧 UUID の対応は `device_legacy_ids` に移行記録として保存する。

down は端末の UUID 外部キーを復元するが、新しい登録者履歴と IMEI の管理情報を削除する。実データに対するロールバックはバックアップを取り、以前のアプリケーションと合わせて行う。

attestation の条件、アプリのパッケージ名・署名証明書 SHA-256 の設定、チャレンジ取得と Android 側の手順は [android-key-registration.md](android-key-registration.md)。
