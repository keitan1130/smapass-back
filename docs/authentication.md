# ログインを使わないアプリ認証

## 方針

利用者のアカウント、メールアドレス、パスワード、ログイン画面、Google ログインは作らない。端末は UUID で識別し、初回登録・再登録には IMEI 全桁を使う。アプリは最初にチャレンジを取得し、IMEI・公開鍵・attestation・秘密鍵での署名を送って、端末の現在の登録期間に結び付いた認証情報を受け取る。

公開 URL には端末 UUID を使う。IMEI 検索は公開のため、IMEI を知っていること自体を認証に使えない。書き込みでは、サーバーが発行したアクセストークンを `Authorization: Bearer ...` で送る。IMEI、CORS の Origin、JSON の所有者 ID だけでは書き込みを許可しない。トークンはアプリ内部で管理し、利用者にログイン操作を求めない。

初回の IMEI 申告だけでは認証情報を発行しない。使い捨てチャレンジと Android のハードウェア鍵 attestation・秘密鍵の保有確認を必須にする。IMEI 自体の実機同一性の証明は通常の key attestation と別なので、検証範囲と必須設定は [Android 鍵登録](android-key-registration.md) を参照。

## Android からの接続手順

1. 初回は `POST /api/auth/challenges` に IMEI を送ってチャレンジを取り、Android Keystore で新しい鍵・attestation・署名を用意する。`POST /api/auth/devices` に IMEI・公開鍵・証明書チェーン・署名を送り、認証情報をアプリ内に保存する。
2. 初回登録で公開鍵も保存される。鍵交換は `/api/devices/key-challenges` のチャレンジで新しい鍵を生成し、`POST /api/devices` に `device_id`・公開鍵・検証証跡を送り、アクセストークンを付ける。
3. 認証が必要な API には常にアクセストークンを付ける。対象の端末 UUID は登録・更新応答の `device_id` で確認できる。
4. アクセストークンが期限切れになったらリフレッシュトークンで更新し、返された2つのトークンを両方置き換える。
5. 認証情報だけを止める場合は `/api/auth/revoke`、売却などで登録も終了する場合は `/api/devices/{id}/revoke` を呼ぶ。

Android から Origin ヘッダーを送る必要はない。実運用の接続先は HTTPS とする。Android 側の画面・通信処理・安全な保存処理はこのリポジトリでは実装しない。トークンを URL、アクセスログ、共有用の証明書、端末の署名対象 payload へ入れない。

## 発行

```http
POST /api/auth/devices
Content-Type: application/json

{"imei":"490154203237518","public_key":"<P-256 公開鍵 PEM>","proof":{"challenge_id":"<チャレンジID>","certificate_chain":["<DERをBase64>","<中間証明書・ルート>"],"signature_der":"<署名DERをBase64>"}}
```

成功は201。`device_id`（端末UUID）、`access_token`、`refresh_token`、`token_type: "Bearer"`、`expires_in: 900`、`refresh_expires_at` を返す。この時点で公開鍵も保存済みで、`POST /api/devices/lookup` で確認できる。検証方法は [鍵登録の接続手順](android-key-registration.md#初回登録初期化後の再登録) を参照。

使用中の端末へ別の認証情報を発行する操作は409。認証情報を取得する目的でこの API を毎回呼ばない。同じIMEIを再送しても、既存の認証情報を返したり、その登録者に成り代わったりはできない。

新しい登録を許可する条件は、現在の登録がない場合、現在の登録者が手動で登録を終了した場合、または最終検証済みログのサーバー受信から3日経過した場合。ログ未受信なら登録開始時刻を使う。切り替え時は旧認証情報・鍵を失効する。端末UUID単位の過去の計測履歴と最新状態の公開参照は継続する。同時に申請されても1件だけ成功する。

3日経過後も、別の登録者が再登録するまでは元の登録は有効。元の端末は有効なリフレッシュトークンで認証情報を更新して通信を再開でき、署名検証済みの新規ログ受信で3日間を数え直す。更新だけ・同一ログの再送は活動時刻を延長しない。持ち主の切り替え後は旧認証情報を使えない。

アプリ削除・初期化・発行応答の消失などでリフレッシュトークンを失った場合も、IMEI だけで即時再発行はしない。この場合は3日ルールによる再登録が必要になる。利用中のアプリで安全に引き継げる場合は、先に登録の手動失効を行う。

## 更新

```http
POST /api/auth/refresh
Content-Type: application/json

{"refresh_token":"<現在のリフレッシュトークン>"}
```

成功は200で新しいトークン一式を返す。アクセストークンは15分、リフレッシュトークンは発行・更新から30日有効。更新のたびに両方を入れ替え、旧アクセストークンと旧リフレッシュトークンは使えなくする。更新は登録期間の3日判定を延長しない。

使用済みリフレッシュトークンの再利用を検出した場合は401を返し、同じアプリ登録の新しいトークンも失効させる。アプリ側で更新処理を1つにまとめ、同時更新や使用済みトークンの自動再送をしない。通信結果が不明な場合も旧トークンを再利用すると失効するため、再試行で必ず復旧できる仕様ではない。

期限切れ、不明、失効済み、前の登録期間のトークンは401。更新 API にアクセストークンや IMEI を送っても更新できない。

## 失効の違い

| 操作 | 対象 | 次の登録 |
| --- | --- | --- |
| `POST /api/auth/revoke`、本文は `refresh_token` | そのアプリ登録の全アクセストークン・リフレッシュトークン | 端末登録は残る。通常の3日ルールを適用 |
| `POST /api/devices/{id}/revoke`、Bearer 必須 | 現在の端末登録・その認証情報・鍵。履歴と最新状態は維持 | 新しいアプリがすぐ登録可能 |

いずれも成功は204。認証情報の失効は知らないトークン・繰り返しも204とし、存在を漏らさない。更新前のリフレッシュトークンでも同じアプリ登録の認証情報を失効できる。端末登録の終了はUUIDを指定する。他端末・不存在は404。証明書単位の失効は行わない。


## 保存と権限の実装

- アクセストークンとリフレッシュトークンは、それぞれ暗号学的乱数32バイトを Base64url にする。JWT や IMEI から計算した値は使わない。
- `app_tokens` には SHA-256 のハッシュだけを保存する。応答以外でトークンを返さず、DB から元のトークンを復元できない。更新済みハッシュは再利用検知のため保持する。
- `app_installations` は端末UUIDの `device_id` と登録期間を持ち、利用者のアカウントは持たない。アプリ登録自身の `id` と端末の `device_id` は別の識別子。
- 各リクエストで、トークンの期限・更新・失効と、登録期間が現在も有効かを DB で確認する。鍵、ログ、登録の書き込みは、端末をロックした同じトランザクション内でも認証情報と対象への権限を再確認する。
- ロック順は端末 → アプリ登録 → トークン。更新・失効・登録者変更と書き込みが競合しても、権限確認と書き込みの間で他人の登録に変わらないようにする。
計測ログの書き込みは `authorization.RequireDevice` を端末ロック後・保存前の同一トランザクションで呼び、現在の登録・認証・鍵を再確認する。

認証情報・チャレンジ・attestationは `000001_initial_schema` にまとめた。以前の `AUTH_PUBLIC_KEY` / `AUTH_ISSUER` / `AUTH_AUDIENCE` は使用しない。既存の外部 JWT を受け入れたり、クライアント指定の所有者 ID を信頼したりする互換設定はない。

更新時のローテーションと再利用検知は [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14) を参考にしている。この API はサービス専用の認証で、OAuth サーバーとしての互換性を提供するものではない。

現行初期定義のdownは全テーブルを削除する。既存DBの通常の更新・移行手順として実行しない。

登録終了でも元ログと公開鍵は残し、同じ公開UUIDで全履歴を参照する。証明書単位の失効・再発行は行わない。
